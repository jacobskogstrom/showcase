What the research found

⚡ Prefill isn't the bottleneck

Flash-Lite: ~0.29s to first token, sub-second overall. Prefill is parallel — 1k vs 10k input tokens costs tens of ms, not seconds. The real cap on turn time is the 300-token spoken-answer output limit, unrelated to context size.

💾 Caching is already on, unused

OpenRouter + Gemini 2.5+ implicit caching is on by default: cached tokens read at 90% off, 80-300ms. Requires a byte-identical prefix across calls — server.py already structures requests that way. A static daily block rides this for free.

🔍 Keyword search beats a vector DB here

Corpus is small, personal, mostly factual (names, dates, decisions). BM25-style lexical retrieval is sub-ms and needs no embeddings pipeline — the right tool for what's actually being looked up.

Why the deep tier felt so much better

📅 Live tool access

Jacob noticed the deep tier (claude -p) checked email and calendar live via gws and gave sharp, current answers. The fast tier only ever sees a snapshot up to 18h stale, and has no email view at all — that's the real gap, not raw context size.

🔁 Fix: refresh once per session, not per turn

A live gws call per voice turn would be too slow. Firing it once when the WebSocket connects — then reusing it for the rest of that session — gets deep-tier freshness at fast-tier speed.

Three-layer architecture (v02)

A. Static, cached ~6-7k tok · refreshed daily 06:00 SYSTEM_PROMPT + about-me + about-business + priorities + connections + learned-facts B. Session-fresh ~300-500 tok · refreshed once per WebSocket connect live calendar (gws) + email digest (unread count, subject/sender/time only) C. Per-turn retrieval ~500-800 tok · refreshed every turn BM25 top-3 hits vs full decisions log + full contacts └─ history (last N turns, appended after)
Only layer A needs to stay byte-identical to earn the caching discount. B and C are cheap in absolute terms, so paying full price on a few hundred tokens each turn barely matters.
