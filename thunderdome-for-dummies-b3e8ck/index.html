Thunderdome for Dummies

What it means when a company says "we run Thunderdome" for its code, why anyone would do something that sounds that reckless, and what it takes to make it work.

Source: yegge.ai/essays/the-shape-of-things-to-come. Written 2026-09-27 for Jacob Skogström (Scandinavian Communication). Claims are Yegge's unless marked as our take.
In one breath

Thunderdome means: stop queueing code changes and testing them one by one before they land. Let every change land on the main branch at once, accept that main goes red, and have a swarm of AI agents find and fix the breakage in parallel. It is faster than the careful way once machines, not humans, write most of the code.

The old way, in kitchen terms

Picture a restaurant with one pass-through window to the dining room. Every plate stops there. A checker inspects it, and only then does it go out. That window is the merge queue. Every code change (a "commit" or "merge request") waits in line. The build system tests each one, or a small batch, before it is allowed onto main, the shared copy of the code everybody works from.

When a batch fails, the system plays detective. It splits the batch in half, tests each half, splits again, and so on until it finds the one plate that was bad. That search is called bisection. It is clever and slow, and it holds up every plate behind it.

This works fine when a team of humans produces a few dozen changes a day. Main stays green almost always. Everyone trusts it.

Why it breaks when AI writes the code

Yegge runs his 30-year-old game Wyvern with a crew of AI agents instead of a human team. The numbers change the whole picture:

175
commits per day on average, peaks around 250
100+
merge requests stuck in the queue while bisection hunted for one failure
~700
designed pieces of work waiting to be built
18
"crew" agents designing work, plus a fleet of worker agents building it

At that rate the pass-through window is the bottleneck. The kitchen cooks faster than the checker can check. Agents sit idle waiting for the queue. The safety mechanism costs more than the failures it prevents.

Thunderdome: everyone into the arena

The name comes from Mad Max. Everyone enters the same arena at once and it gets sorted out inside. Yegge also calls it the Land Rush. The idea:

1. Land it all
When the queue backs up, every waiting change lands on main at the same time. No gate, no batching, no bisection.
2. Main goes red
Tests fail. That is expected and accepted. Main is no longer sacred.
3. Swarm
Several agents diagnose the breakage in parallel, each on a different failure, instead of one process hunting serially.
4. Fix forward
Agents push fixes. Main turns green again, faster than bisection would have found the first culprit.
5. Release elsewhere
Customers never see red main. Shipping happens from separate, stable release branches.
"Agents can diagnose red-main problems way faster than the bisection process handles it."Steve Yegge, the essay

The shift in one sentence: stop spending effort preventing breakage, spend it recovering from breakage fast. Prevention is a queue. Recovery is parallel.

This is not new, game studios did it first

Big video game studios have worked this way for years. They call it Game DevOps. Dozens of builds land on main every day, main is often broken, and the studio ships from release branches it keeps stable on the side. Perforce, the version-control vendor most AAA studios use, documents it as standard practice. Thunderdome takes that model and hands the clean-up job to AI agents.

What a company needs before it can run Thunderdome

Lots of agent capacity

The whole model rests on many agents working at once. Yegge rotates 12 Max subscriptions to get what he calls "infinite tokens". Wyvern burns roughly 87 000 dollars a month in list-price token value, which the rotation trick brings down to about 2 800 dollars.

A work tracker agents can read

Yegge's is called Beads: an issue tracker that doubles as a knowledge graph, versioned in git. Every task is a small atomic unit with dependencies and gates, so agents can pick work up without a human handing it over.

Standing role agents

Not just task workers. Agents with permanent jobs, running unattended: an SRE agent watching production, an abuse-monitoring agent, a fleet manager ("the Marshal"). About 45 cron jobs wake them up.

Release branches and fast tests

Red main only works if customers never touch main. You need stable release branches, and tests fast enough that "red" is a signal you see in minutes, not hours.

What changes for the developers

  • Human code review mostly disappears. Yegge keeps it only where an auditor demands it (SOC 2). Agents review agents.
  • Nobody waits for the merge queue. There is no queue.
  • The job shifts from writing code to designing work and running the fleet. Yegge's crew agents write designs. Worker agents implement them. Humans steer.
  • Mindset shift: tolerate productive chaos. A red main is no longer an emergency. It is Tuesday.
  • Stakeholders ask, agents deliver. His "Wish Factory" lets users file a wish as a GitHub issue or an in-game command, and agents build and deploy it.

MainThe shared master copy of the code. Traditionally kept "green" (all tests passing) at all costs.

BisectionFinding the one bad change in a failed batch by repeatedly splitting the batch in half. Slow at scale.

WheelhouseYegge's orchestration system that runs all of the above, controlled from Emacs.
Game DevOpsThe game-studio precedent: many builds on main daily, ship from release branches.

Should a normal company do it? Our take

This section is not from the essay. It is the honest reading of it for a normal company.

  • Thunderdome is a symptom of scale, not a best practice to adopt. It only pays off once the commit rate is far beyond what humans produce. Below roughly a hundred commits a day, a merge queue is not the bottleneck and red main is pure cost.
  • The prerequisites are the hard part. Agent capacity, an agent-readable tracker, standing role agents, release branches, fast tests. Without all five, "Thunderdome" is just a broken main with a cool name.
  • If a company says it runs Thunderdome, ask three questions. How many commits a day? Where do customers ship from? Who or what fixes red main, and how fast? Good answers: hundreds, release branches, agents within minutes.
  • Yegge's bigger claim is worth taking seriously anyway. He argues every software company will converge on a bespoke "city" of agents with its own roles and rules, and that gatekeeping practices like human review and classic CI/CD become relics within about a year. Agree or not, that is the direction any company running Thunderdome is betting on.
